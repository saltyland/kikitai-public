# 技術選定の記録（ADR）

最終更新: 2026-08-11

各判断について「何を選んだか」だけでなく、**何を捨てたか / どんな代償を受け入れたか** を残す。

---

## ADR-001 Next.js 16（App Router）を採用する

**文脈**
個人〜2 名規模で、認証・DB アクセス・LLM 呼び出しを含む Web サービスを作る必要があった。
API サーバーを別に立てる余力はない。

**決定**
Next.js 16 の App Router + Server Actions を採用し、フロントとバックエンドを 1 リポジトリに統合する。

**理由**
- Server Actions により、フォーム送信の処理をサーバー側だけで完結できる。LLM の API キーや Supabase の service role キーがクライアントに漏れる経路が構造的に存在しない
- Server Components で DB 取得結果をそのまま描画でき、状態管理ライブラリが不要
- Vercel へのデプロイが実質ゼロ設定

**代償 / 既知のリスク**
- Next.js 16 は破壊的変更が多く、`cookies()` / `params` / `searchParams` が非同期化、`middleware.ts` が `proxy.ts` に置き換わった。学習済み知識やネット上の情報がそのまま使えない場面が頻発した
- Vercel への依存が強い（Cron を含む）

**却下した案**
- *React SPA + 別途 API サーバー*：認証・CORS・デプロイ先が二重になり、2 名では保守しきれない
- *Rails / Django*：フロントの体験（アンケート作成 UI のドラッグ&ドロップ等）を作り込むには不利

## ADR-002 Supabase（PostgreSQL + Auth + RLS）を採用する

**文脈**
「他人の回答内容が見えてしまう」事故は、このサービスでは致命的（研究倫理上の問題になる）。
アプリ層の認可チェックだけに頼りたくない。

**決定**
Supabase を採用し、**全テーブルで Row Level Security を有効化**する。認可は DB に寄せる。

**理由**
- アプリ層で認可条件を書き忘れても、DB が最後の砦になる
- 他人のプロフィールは `points` / `trust_score` を落とし `private_fields` でマスクした `public_profiles` ビュー経由でしか読めない、という制約を SQL 側で表現できる
- PostgreSQL の RPC 関数を使えるため、ポイント整合性をトランザクションに閉じ込められる（ADR-004）
- 認証・DB・ストレージが 1 サービスで揃い、無料枠で始められる

**代償**
- RLS ポリシーが増えるとデバッグが難しい（「なぜ 0 行返るのか」の切り分けコスト）
- ベンダーロックインが発生する。ただし中身は素の PostgreSQL なので移行不能ではない

**却下した案**
- *Firebase*：リレーショナルな集計（クロス集計・属性別分析）が主要機能なので不利
- *自前 PostgreSQL + 自前認証*：運用コストが 2 名規模に見合わない

## ADR-003 ポイントを「有効期限つきロット」で管理する

**文脈**
単純な残高整数（`profiles.points`）だけで管理すると、
「ポイントを貯め込んで誰も回答しない」状態と「失効の実装ができない」問題が同時に起きる。

**決定**
付与のたびに `point_lots`（金額・付与日時・失効日時）の行を作り、
残高は「期限内ロットの合計」として算出する。消費は付与日時の古い順（FIFO）。

**理由**
- 180 日で失効させることで、貯め込みより「使う」方が合理的になり、市場の循環が止まらない
- FIFO により、失効が近いポイントから消費されユーザーの不利益が最小になる
- 「いつ・なぜ付与されたか」の履歴がそのまま残り、失効予告通知が実装できる

**代償**
- 残高参照が集計になるため、`profiles.points` にキャッシュを持つ必要が生じた（`sync_points_balance` で同期）
- 消費時にロットの分割・削除が発生し、ロジックが単純な減算より複雑

## ADR-004 ポイント操作を PostgreSQL の RPC 関数に閉じ込める

**文脈**
当初はアプリ層で「残高を読む → 計算する → 書き戻す」形で実装していた。
同時に複数の回答が送信されると **lost update** が発生し、残高がずれる。

**決定**
`consume_points` / `publish_survey` / `submit_survey_response` / `sync_points_balance` を
PostgreSQL の関数として実装し、アプリ層は 1 回の RPC 呼び出しだけを行う。

**理由**
- 行ロック（`FOR UPDATE`）と単一トランザクションで、同時実行時の整合性を DB に保証させられる
- 「回答は保存されたがポイントが付与されていない」という中途半端な状態が原理的に発生しない
- 残高同期を 1 文の `UPDATE ... SET points = (select sum ...)` にすることで read-modify-write を消せる

**代償**
- ビジネスロジックが SQL とアプリに分散する。特に設問タイプ別単価（`question_point_cost`）は
  SQL 側と `lib/domain/questions/` の両方に存在し、**同期を人手で保つ必要がある**（既知の負債）
- SQL のテストが書きにくい

**補助的な決定**
ビジネスエラーは `KIKITAI:<CODE>:<詳細>` 形式で `raise exception` し、
`lib/repositories/dbError.ts` の 1 箇所で日本語メッセージへ変換する。

## ADR-005 品質評価を「ルールベース + LLM」の 2 層にする

**文脈**
LLM だけに採点させると、(a) API 障害でサービスが止まる、(b) プロンプトインジェクションで
スコアを吊り上げられる、(c) 誤判定で真面目な回答が 0pt になる、という 3 つのリスクがある。

**決定**
外部依存のないルールベース評価を第 1 層として必ず実行し、
LLM 評価は第 2 層として条件付きで呼ぶ。両者を `CompositeEvaluator` で合成する。

**理由**
- LLM が全滅してもルールベースだけで評価が成立する（サービスが止まらない）
- LLM スコアがルールスコアを 15 点以上上回る場合は「吊り上げ疑い」としてルールスコアを上限にできる
- `mechRisk < 0.15`（機械的にはまったく怪しくない）なら最低 30% を保証する安全弁を置ける
- 自由記述がない回答では LLM を呼ばずに済み、コストとレイテンシを削減できる

**代償**
- 合成ロジックが直感的でなく、「なぜこのスコアになったか」の説明コストが高い
- 2 つの評価器の整合性をテストで担保する必要がある（`index.test.ts` ほか）

## ADR-006 同期採点に「締切」を設ける

**文脈**
LLM、特に CPU 推論のローカル LLM は数十秒かかることがある。
回答者を送信画面で待たせると、サービスの根幹である「回答する体験」が壊れる。

**決定**
同期採点に締切（`QUALITY_DEADLINE_MS`・既定 4000ms）を設ける。
締切を超えたら機械評価スコアで即確定し、走り続ける LLM 評価は
Next.js の `after()` で応答送信後の「背景監査」に回す。

**理由**
- どのプロバイダがどれだけ遅くても、回答者は必ず締切以内に**確定値**を受け取る（後から増減しない）
- 背景監査で「即時確定値と LLM 評価の乖離」を記録でき、較正データとして蓄積できる
- レイテンシを SLA としてコードで表現できる

**代償**
- 遅い環境では LLM 評価が実質使われず、機械評価のみで確定するケースが増える
- 即時確定値と背景監査の結果が食い違ったとき、ポイントを事後調整しない（Phase 4 の課題として残す）

## ADR-007 ティア閾値をコードから追い出す（`calibration.json`）

**文脈**
5 段階の付与率を決める閾値は、運用しながら何度も調整することが確実だった。
そのたびにコード変更とデプロイが必要なのは現実的でない。

**決定**
閾値・救済値を `calibration.json` に外部化し、`grade()` が起動時に一度読み込む。
値は人手ラベル 400 件からロジスティック回帰（`scripts/calibrate_phase3.py`）で自動算出する。

**理由**
- ファイル差し替えだけで運用調整でき、再デプロイが不要
- 「FNR ≤ 10% を優先し FPR は許容する」という**非対称コスト**を、PR 曲線上の動作点選択として明示的に扱える
  （真面目な回答を 0pt にするコスト > 手抜きを見逃すコスト）
- 閾値の根拠がスクリプトとして残り、再現できる

**代償**
- 設定ファイルとコードの整合性が崩れると原因追跡が難しい
- ラベル付けに人手コストがかかる

## ADR-008 LLM プロバイダをインターフェースで抽象化し、4 段フォールバックにする

**文脈**
無料枠で回したいが、Gemini は 1500 件/日の上限がある。単一ベンダー障害でも止めたくない。

**決定**
`QualityEvaluator` インターフェースを定義し、
ローカル LLM（OpenAI 互換）→ Gemini 2.5 Flash → Groq → Cerebras → ルールベース の順に落とす。

**理由**
- ローカル LLM（Ollama / LM Studio / llama.cpp）を設定した環境ではクォータを一切消費しない
- 未設定環境（Vercel 本番）では自動的に連鎖から外れ、Gemini が一次になる
- 各プロバイダの実装が独立しているため、追加・削除がテスト付きで安全に行える

**代償**
- プロバイダごとにレスポンス形式の差異を吸収するコードが必要
- 「どのプロバイダで採点されたか」により結果がわずかにぶれる

## ADR-009 DB マイグレーションをすべて冪等に書く

**文脈**
`npm run sync` は DB パスワード未設定時に Supabase Management API 経由で
マイグレーション SQL を直接実行する。この経路では適用済み判定が効かず、再実行が起きうる。

**決定**
全マイグレーションを `create table if not exists` / `add column if not exists` /
`drop policy if exists → create policy` / `drop function if exists → create function` で構成する。

**理由**
- 既存 DB に対して何度流しても壊れない
- 開発メンバーの環境差異による「片方だけスキーマが古い」事故を防げる

**代償**
- SQL が冗長になる
- 関数のシグネチャ変更時は旧シグネチャをすべて `drop` する必要があり、書き漏らすと重複定義になる
  （実際に `pay_per_answer` / `point_economy` で問題が起き、以降 DROP → CREATE 方式に統一した）

## ADR-010 ライセンスをソースアベイラブル（閲覧・評価のみ）にする

**文脈**
受託開発のポートフォリオとして公開するため、コードを読まれる前提の状態にする必要がある。
一方でキキタイは実際に稼働しているサービスであり、今後プロダクトとして育てる可能性がある。

当初は MIT を検討したが、MIT は第三者による複製・改変・再配布・商用利用をすべて許諾する。
「読んで評価してほしい」という目的に対して、許諾範囲が明らかに広すぎる。
また一度 MIT で公開したバージョンは、後から取り消せない。

**決定**
独自のソースアベイラブル・ライセンスを採用する。

| 行為 | 可否 |
|---|---|
| 閲覧・読解 | ✅ 自由 |
| 読解目的のクローン・評価目的のローカル実行 | ✅ 自由 |
| 出典を示した短い引用（レビュー・教育・技術議論） | ✅ 自由 |
| 製品・サービス・社内システムへの組み込み | ❌ 要許諾 |
| 複製・改変・再配布・販売 | ❌ 要許諾 |
| 本コードに基づくサービスの運営・提供 | ❌ 要許諾 |
| 再配布・商用利用目的の ML 学習データ利用 | ❌ 要許諾 |

**理由**
- ポートフォリオの目的（読まれること）は、閲覧・評価の許諾だけで完全に達成できる
- サービスとしての将来の選択肢（商用展開・ライセンス販売・クローズド化）を残せる
- 「ライセンスが無い＝黙示的に全権利留保」の状態より、閲覧してよい範囲が明示されている分、
  レビューする側にとってむしろ親切

**代償**
- OSI 承認ライセンスではないため、GitHub のライセンス自動判定に載らず、
  一般的な OSS としての受け取られ方はしない
- コントリビューションを受け付けにくい（現状 2 名の開発体制では問題にならない）

**再検討の条件**
コミュニティ開発に開く方針へ切り替える場合は、その時点で Apache-2.0 等への変更を検討する。
逆方向（緩い → 厳しい）への変更は既存配布分に効かないため、**厳しい側から始める**判断とした。
