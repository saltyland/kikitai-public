# 要件定義

最終更新: 2026-08-11

---

## 1. 背景と課題

大学の卒論・修論・ゼミ・研究室調査でアンケートを実施する際、共通して次の問題が起きる。

| 課題 | 具体的に何が起きるか |
|---|---|
| 回答者が集まらない | SNS で拡散しても反応が薄く、必要サンプル数に届かない |
| 標本が偏る | 集まるのは知人・同学科ばかりで、属性が偏る |
| 依頼コストが高い | 個別に頼むと人間関係のコストが発生し、断りにくさが回答の質を下げる |
| 回答の質が担保できない | 謝礼つきアンケートでは、報酬目当ての手抜き回答が混入する |

一方で、同じ大学内には「自分もアンケートを配りたい人」が同時に大量に存在する。
**需要（回答者がほしい）と供給（回答できる人）は同じ母集団の中にある** が、両者をつなぐ仕組みがない。

## 2. 解決アプローチ

ポイントを媒介にした**相互扶助型の交換市場**を作る。

```
回答する → ポイントを得る → ポイントを払って自分のアンケートを公開する → 回答が集まる
```

謝礼を現金にしないことで、外部からの報酬目的ユーザーの流入を防ぎ、
「アンケートを配りたい当事者」だけがポイントを稼ぐ動機を持つ設計にする。

ただしこのままでは **「雑に答えてポイントだけ稼ぐ」フリーライド** が成立してしまう。
そこで回答の質を AI が評価し、付与ポイントを質に比例させることを本サービスの中核とする。

## 3. スコープ

### 3.1 対象ユーザー

| 区分 | 説明 |
|---|---|
| 主対象 | 大学生・大学院生・研究者（アンケートを配る側と答える側を兼ねる） |
| 副対象 | 研究室・ゼミ単位での利用 |
| 対象外 | 企業のマーケティング調査、一般消費者パネル |

### 3.2 Phase 定義

| Phase | 内容 | 状態 |
|---|---|---|
| Phase 1 | 認証・アンケート作成・回答・結果確認（MVP） | ✅ 完了 |
| Phase 2 | ポイント経済、信頼スコア、AI 品質評価 | ✅ 完了 |
| Phase 3 | 品質評価の較正（人手ラベルからの閾値自動算出） | ✅ 完了 |
| Phase 4 | シャドーモード運用、事後信頼スコア減点 | 🔜 構想 |
| 将来 | Google Forms / Qualtrics インポート、ORCID 連携、多言語対応 | 🔜 構想 |

## 4. 機能要件

### 4.1 ユーザー管理

| ID | 要件 |
|---|---|
| U-1 | メールアドレスとパスワードで登録・ログイン・ログアウト・退会ができる |
| U-2 | 公開プロフィール（ニックネーム・所属・研究分野・SNS リンク）を設定できる |
| U-3 | 属性（学年・専攻・職種・年齢・性別・誕生日）を任意で登録でき、項目ごとに非公開にできる |
| U-4 | 退会時は `auth.users` ごと削除され、関連データがカスケード削除される |
| U-5 | 登録せずにデモを試せる（ゲスト経路） |

### 4.2 アンケート作成

| ID | 要件 |
|---|---|
| S-1 | 9 種の設問タイプを使える（単一選択 / 複数選択 / プルダウン / 記述式 / 段落 / 日付 / スケール / グリッド / アテンションチェック） |
| S-2 | 設問の必須化・説明文・並べ替え・複製ができる |
| S-3 | セクション（ページ分割）と条件分岐を設定できる |
| S-4 | 回答対象を属性・信頼スコア下限で絞り込める |
| S-5 | インフォームドコンセント文を設定でき、回答前に必ず表示される |
| S-6 | 下書き / 公開 / 終了 の状態を持ち、遷移は状態機械で制御される |
| S-7 | 全体公開と限定公開（URL 共有）を選べる |
| S-8 | AI が設問案を自動生成・改善提案する |
| S-9 | 公開時に「必要回答数 × 設問コスト」のポイントを消費する |

### 4.3 回答

| ID | 要件 |
|---|---|
| A-1 | 自分の属性・信頼スコアに合致し、自作でも回答済みでもないアンケートのみ表示される |
| A-2 | 同意画面を経てから回答を開始する |
| A-3 | セクション送りと進捗バーで回答状況がわかる |
| A-4 | 必須設問の未回答を送信前に検出する |
| A-5 | 同一アンケートへの重複回答ができない |
| A-6 | 送信直後に品質評価スコアと獲得ポイントが表示される |

### 4.4 ポイント経済

| ID | 要件 |
|---|---|
| P-1 | ポイントは付与単位（ロット）で管理され、付与から 180 日で失効する |
| P-2 | 消費は付与日時の古い順（FIFO）で行われる |
| P-3 | 残高不足の公開操作は失敗し、状態を変更しない |
| P-4 | 設問コストは設問タイプごとに異なる（選択式 0.5 / 記述式 1.0 / 段落 2.0 / グリッド 1.5） |
| P-5 | 回答への付与額は品質ティアに応じて コスト × 0 / 0.3 / 0.5 / 0.8 / 1.0 |
| P-6 | 高品質回答が集まった場合、作成者にも消費コストの一部が還元される |
| P-7 | 失効予定のポイントは事前に通知される |

### 4.5 品質評価

| ID | 要件 |
|---|---|
| Q-1 | ルールベース評価（所要時間・一直線回答・定型句率・設問丸写し・回答使い回し 等 9 規則）でスコアを出す |
| Q-2 | 自由記述がある場合は LLM が 4 軸（関連性・具体性・一貫性・誠実性）で採点する |
| Q-3 | LLM の応答が遅れても、回答者は既定 4 秒以内に確定スコアを受け取る |
| Q-4 | アテンションチェック不正解は無条件で付与率 0% とする |
| Q-5 | LLM 単独の誤判定で真面目な回答を 0pt にしない安全弁を設ける |
| Q-6 | ティア境界値は設定ファイルで変更でき、コード変更・再デプロイを要しない |
| Q-7 | LLM へは設問文と回答テキストのみを送り、ユーザー ID・属性・IP を送らない |

### 4.6 結果分析

| ID | 要件 |
|---|---|
| R-1 | 作成者のみが回答一覧・集計を閲覧できる |
| R-2 | 設問タイプに応じた集計グラフを表示する |
| R-3 | グリッド設問のクロス集計ができる |
| R-4 | CSV / Excel でダウンロードできる |
| R-5 | サマリーレポートを出力できる |

### 4.7 ソーシャル / 通知

| ID | 要件 |
|---|---|
| N-1 | ユーザーをフォローでき、フォロー中ユーザーのアンケートが優先表示される |
| N-2 | トピックをフォローでき、関連アンケートのダイジェスト通知を受け取れる |
| N-3 | 通知センターで未読・既読を管理できる |
| N-4 | 通知の種類ごとに受信可否を設定できる |

## 5. 非機能要件

| 区分 | 要件 |
|---|---|
| **応答性** | 回答送信から採点結果表示までを既定 4 秒以内に構造的に保証する（`QUALITY_DEADLINE_MS`） |
| **整合性** | ポイントの二重付与・残高マイナスを発生させない。付与・消費は単一トランザクションで完結する |
| **認可** | 全テーブルで Row Level Security を有効化し、アプリ層のバグが直ちに情報漏洩にならない構成にする |
| **プライバシー** | 他人のプロフィールは `points` / `trust_score` を除外し、`private_fields` 指定項目をマスクしたビュー経由でのみ参照可能 |
| **データ保持** | アンケートに保持期限を設定でき、超過データは日次バッチで自動削除する |
| **可搬性** | AI 評価の外部 API が全滅してもルールベース評価だけでサービスが動作する |
| **可用性** | LLM プロバイダは 4 段のフォールバック連鎖を持ち、単一ベンダー障害で停止しない |
| **セキュリティ** | HSTS・`X-Frame-Options`・`X-Content-Type-Options`・`Referrer-Policy`・`Permissions-Policy` を全レスポンスに付与。匿名アカウント作成は Cloudflare Turnstile で保護 |
| **保守性** | UI から DB を直接参照しない 4 層構成。DB マイグレーションはすべて冪等 |
| **検証性** | ドメインロジックは外部依存を持たず単体テスト可能。CI で型・Lint・テスト・ビルドを必須化 |
| **倫理** | 研究倫理審査に耐えるよう、回答前のインフォームドコンセント表示を必須とする |

## 6. 対象外（やらないと決めたこと）

| 項目 | 理由 |
|---|---|
| ポイントの現金化・換金 | 報酬目的の外部ユーザー流入を招き、回答品質が崩壊するため |
| ネイティブアプリ | PWA で足りる。開発・審査コストに見合わない |
| リアルタイム共同編集 | 個人の調査設計が主用途で需要が薄い |
| 完全匿名での回答 | 重複回答防止と信頼スコアが機能しなくなるため（限定公開のみ例外的に許容） |
